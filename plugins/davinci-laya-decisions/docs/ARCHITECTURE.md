# Устройство: как принимаются решения

## Поток данных

```
ZCode (основная модель)
  │
  ├─ PreToolUse(Bash|Write|Edit|MultiEdit)
  │     └─ hooks/pre-tool.mjs → gates.preToolGate
  │          1. детерминированные правила (без модели)  ─┐
  │          2. сборка короткого state, маскирование      │ → решение: none|log|ask
  │          3. Laya /decide (3 вопроса, ~35 мс)         ─┘   (allow/deny не существует)
  │          4. метрики + ledger                           stdout: пусто либо permissionDecision=ask
  │
  ├─ PostToolUse / PostToolUseFailure
  │     └─ recordToolUse: изменённые файлы, проверки и коды, неразрешённые ошибки, git status
  │        stdout всегда пуст (не подменяем вывод инструмента)
  │
  ├─ Stop
  │     └─ evaluateDoneGaps (детерминированно) + Laya (только при пробелах)
  │        report: молчание | block: одна блокировка на сессию
  │
  ├─ UserPromptSubmit
  │     └─ классификация задачи в метрики; advise — одна строка контекста
  │
  └─ MCP (stdio, 10 инструментов) → тот же Laya-клиент
        решения/ранжирование; вытесненное сохраняется в chunks/
```

## Слои защиты RiskGate

Решения принимаются **послойно**, и слои имеют разный вес:

1. **Детерминированные правила** (`decision-policy.mjs`, ~30 правил + составные
   проверки). Не зависят от модели, работают при недоступной Laya, FNR=0 на
   наборе из 35 опасных кейсов, FPR=0 на 21 безопасном. Это единственный слой,
   который может **эскалировать** вызов.
2. **Комбинированные проверки**: «сетевой инструмент + секрет в аргументах»
   (эксфильтрация), «запись вне workspace/в системный каталог», «секретный путь».
3. **Laya** — вероятностная оценка для неоднозначного. Даёт `risk_class`,
   `data_loss`, `exfiltration` и калиброванную `answer_confidence`. Может
   эскалировать только при уверенности ≥ порога и **доверенном** ответе
   (нет обрезки/схлопывания). Никогда не отменяет слой 1 и никогда не разрешает.

Решение: `ask` = (правило high) OR (Laya high ∧ p ≥ порог ∧ trustworthy).
Всё остальное — `log`. Класса `allow` в политике нет по конструкции.

## Почему Laya не может быть единственным барьером

Измерено на живом чекпоинте (`scripts/laya-eval.mjs`): Laya ставит `high` лишь
7 из 35 опасных команд и ноль ложных `high` на 21 безопасной. То есть у модели
высокая точность при низкой полноте — **именно поэтому** правила дают полноту,
а Laya добавляет осторожность без ложных тревог. Обратный порядок (доверять
вероятности как факту) дал бы FNR ~80%.

## Fail-open: что происходит при сбоях

| Сбой | Поведение |
|---|---|
| Laya не запущена / порт закрыт | решение строится только на правилах; в метрику пишется `inference_error` |
| Таймаут (`timeoutMs`, по умолч. 1500 мс) | то же; `AbortController` не даёт хуку висеть (жёсткий лимит хука 5000 мс) |
| Ответ не проходит схему (нет `answer_confidence`, чужой `version`) | ответ отбрасывается целиком: «почти ответ» хуже отсутствия ответа |
| Серия сбоев | circuit breaker (файл `state/circuit-breaker.json`, 5 сбоев → пауза 30 с). Хук-процессы не разделяют память, поэтому состояние предохранителя — файл |
| Обрезка state / схлопнутые варианты | ответ помечается `trustworthy: false`, эскалация по нему запрещена |
| Ошибка внутри хука | `runHook` ловит всё: диагностика в stderr, stdout пуст, exit 0 — ZCode продолжает работу |

## Память и состояние

- **Ledger** — файл на сессию. Пишут хуки, читают Stop и MCP. Атомарная запись
  (tmp+rename), чтобы параллельные хуки не рвали файл. Хранит факты, не содержимое.
- **Метрики** — JSONL на день: `kind, session_id, tool, mode, action, reason,
  latency_ms, checkpoint, question_set_version, state_hash, scores, inference_error`,
  доля обрезок. Текст команд/промптов не пишется (проверяется тестом с «канарейкой»).
- **Chunks** — вытесненные фрагменты (`ctx-…`, `log-…`, `search-…`). `laya_get_chunk`
  возвращает полный текст; при переполнении удаляются самые старые (лимит в конфиге).
  Политика: вытеснить ≠ удалить.

## Производительность хуков: лаунчер

ZCode запускает каждый хук отдельным процессом, и на Windows старт Node стоит
~100–200 мс на событие. Для явно читающих команд (`ls`, `cat`, `git log`, `rg`)
гейту проверять нечего — поэтому pre-tool/post-tool идут через
`bin/laya-hook.exe` (Go, ~24 мс): он пропускает такие события **не запуская Node**
и передаёт всё остальное в Node без изменений.

Безопасность пропуска устроена как **whitelist**, а не blacklist: команда
пропускается только если (а) это `Bash`, (б) она начинается с известной читающей
команды, (в) в ней нет цепочек/конвейеров/перенаправлений/подстановок, (г) она не
касается путей с секретами (`.ssh`, `.aws`, `.env`, `id_rsa`, `credentials`…) и
(д) политика не `always`. Любое сомнение — проброс в Node. Набор из 35 опасных и
21 безопасного кейсов прогоняется через сам бинарник (`tests/launcher.test.mjs`,
84 проверки): опасное не пропускается никогда.

`git status` намеренно НЕ в списке пропуска: post-tool берёт из него доказательство
состояния дерева для ledger, и пропуск стоил бы точности гейта.

## Границы расширения ZCode, которые учтены

- `PreToolUse` умеет `allow/ask/deny` и `updatedInput` (полная замена, не патч).
  Плагин использует **только** `ask`; `updatedInput` не трогает.
- `PostToolUse` **не может** заменить вывод инструмента — поэтому ContextSelector
  реализован как MCP-инструменты, а не как «умный хук».
- `UserPromptSubmit` не может переключить модель и не может переписать запрос
  штатным хуком — TaskRouter только рекомендует.
- `Stop` допускает максимум 3 продолжения подряд; плагин ограничивает себя одним
  блоком на сессию плюс учитывает `stop_hook_active`.
- Проектные хуки в `<workspace>/.zcode/config.json` не исполняются — поэтому всё
  упаковано в плагин.

## Почему MCP-сервер написан без зависимостей

MCP-stdio — это построчный JSON-RPC 2.0. Реализация на голом Node (`mcp-server.mjs`,
~150 строк) означает: нет `npm install`, нет сборки, нет `node_modules` в плагине —
и, значит, нет «тихой» цепочки поставок. Дополнительно: сервер не пишет файлы вне
своего каталога данных и не исполняет внешних команд.
