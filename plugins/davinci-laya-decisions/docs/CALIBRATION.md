как именно мерить и что считать результатом.

## 2. Качество гейта (FNR/FPR)

```cmd
node scripts/laya-eval.mjs [порог]
```

Прогоняет 35 опасных и 21 безопасный кейс (`tests/fixtures-risk.mjs`) через
слои гейта на живом сервере.

Свежий замер (RTX 3060, чекпоинт fp16):

```
Детерминированные правила: FNR=0/35, FPR=0/21
Laya risk_class=high: опасных 7/35, безопасных 0/21
Laya latency: p50=35 мс, p95=49 мс, max=133 мс
Режим ask: высокий риск → ask 24/24 (100%)
           средний риск  → ask 0/11 (по проекту только лог)
           безопасные    → ask 0/21 (FPR 0.000)
```

Как читать:
- **FNR правил должен быть 0.** Правило, пропустившее опасный кейс, — инцидент:
  именно правила, а не модель, отвечают за полноту.
- **FPR правил должен быть 0** на бытовых командах: ложный `ask` на `git status`
  быстро приводит к тому, что пользователь отключает гейт целиком.
- **Рост «только по мнению Laya»** (сейчас 0) означает, что модель начала
  эскалировать без сигналов правил. Это допустимо, но требует ручного разбора
  нескольких новых кейсов — иначе FPR поползёт незаметно.
- Порог по умолчанию 0.7. Повышение (0.8+) уменьшит число вопросов и увеличит
  пропуски; понижение — наоборот. Проверяй обе цены замером, а не ощущением.

## 3. Латентность и бюджет хука

Замерено интерливингом (7 прогонов на путь, спавн из Node-процесса — как в ZCode):

| Путь | Через лаунчер | Без лаунчера | Δ |
|---|---|---|---|
| `pre-tool` read-only (`ls`, `cat`, `git log`) | **28 мс** | ~200 мс | **−86%** |
| `pre-tool` рискованное (Laya, 3 вопроса) | ~320 мс | ~290 мс | +30 мс |
| `pre-tool` Write/Edit (Laya) | ~327 мс | ~330 мс | ≈0 |
| `post-tool` read-only | **25 мс** | ~180 мс | **−86%** |
| `post-tool` Write/Edit (ledger) | ~174 мс | ~200 мс | −13% |
| `stop` без пробелов | ~274 мс | ~274 мс | 0 |

Разложение (после оптимизаций):

| Компонент | Время | Комментарий |
|---|---|---|
| Старт Go-лаунчера | ~24 мс | спавн процесса (платформенный пол ~22 мс) |
| Старт Node (когда нужен) | ~100 мс | пол `node -e 0`; в ZCode-контексте это минимальная цена любого JS-хука |
| Импорт модулей плагина | ~15 мс | (lazy `node:https` и FNV-хеш убрали дорогие части) |
| Логика гейта + запись ledger/метрик | ~7–80 мс | для событий с записью |
| Вызов Laya | 13 мс + инференс 35–50 мс | node:http вместо fetch: было 73–92 мс только на HTTP |

Что было исправлено по итогам замеров (все три — измеренные, не предположения):
1. **fetch → node:http**: первый `fetch` в свежем процессе инициализирует undici
   и стоит 73–92 мс против 13 мс — при том, что хук всегда свежий процесс.
2. **Go-лаунчер хуков**: для явно читающих команд Node не запускается вовсе
   (кроме `always`-политики) — минус ~170 мс на событие; рискованное и запись
   идут в Node без изменений (+~30 мс на работу лаунчера).
3. **Убраны `node:https` (ленивый импорт) и WebCrypto** из горячего пути:
   TLS-стек и `crypto.subtle` стоили десятки миллисекунд на каждый хук.

Что не сработало (проверено и отклонено):
- `module.enableCompileCache()` — выигрыш 5–10 мс, в пределах шума: Node тратит
  время на собственный bootstrap, а не на компиляцию наших 11 модулей.
- `--snapshot-blob` (пользовательские снапшоты V8) — без выигрыша, а с
  `node:readline` официально не верифицирован.

Что осталось платформенным и не решается кодом: цена запуска любого процесса
на Windows (~22 мс) и старт Node (~100 мс) для событий, где нужен JS. Совет:
исключить каталог плагина и `node.exe` из активного сканирования антивируса —
разница измеряется тем же замером. `layaPolicy: smart` (умолчание) и лаунчер
снимают накладные с самой частой категории вызовов — явно читающих команд.

## 4. Экономия токенов: что считать

Экономия — **не** сумма быстрых вызовов Laya. Считается разница основного
потребления главной модели:

```
NetSavings = baseline_MainLLM_Tokens
           − experiment_MainLLM_Tokens
           − extra_MainLLM_Tokens_from_added_context
```

Важно: если MCP-инструмент отранжировал вывод, но главная модель всё равно
прочитала тот же полный текст, экономии нет — только потраченные вызовы.
Считать (`/usage` ZCode или usage-stats) по сессиям:

1. **A — baseline**: плагин выключен, обычная работа.
2. **B — shadow/gates**: хуки пишут метрики, ничего не меняют.
3. **C — gates + context tools**: модель использует `laya_search_relevant`,
   `laya_log_triage`, `laya_context_pick`.

На каждой конфигурации — одинаковые по сложности реальные задачи, минимум 10–15
сессий. Фиксировать: токены главной модели, `wall_time`, число тяжёлых довызовов
модели, долю пройденных тестов, регрессии/повторные исправления.

**Критерий Этапа 3 ТЗ:** `NetSavings > 0` при сопоставимом проходе тестов.
Если не выполняется — вернуть baseline и не «оптимизировать» дальше.

## 5. Метрики плагина

```cmd
node scripts/laya-admin.mjs status
```

Что там видно и как пользоваться:

| Поле | Смысл | Тревожный сигнал |
|---|---|---|
| `сбоев Laya` | доля вызовов, ушедших в fail-open | > 5% — сервис нестабилен, режим `ask` включать нельзя |
| `action=ask` vs `log` | сколько раз гейт поднимал вопрос | внезапный рост — проверить, не сработала ли новая пара правил |
| `с обрезкой state` | доля ответов с `trustworthy:false` | > 10% — укоротить формулировки state |
| `latency p50/p95` | задержка решений | p95 → 1000 мс — смотреть `device` Laya |
| `чекпоинты` | на каких весах приняты решения | два id одновременно — микс замеров, A/B испорчен |

Сырые данные: `metrics/decisions-YYYY-MM-DD.jsonl` (JSONL, одна строка на решение).
Ничего кроме `state_hash` от текста там нет — делиться файлом безопасно.

## 6. Дисциплина версий

Каждое решение в метриках привязано к:
- `checkpoint` — веса (`multilingual-fp16-<sha12>`);
- `question_set_version` — шаблоны вопросов (`risk-v1`, `done-v1`, `router-v1`);
- `mode` — режим гейта.

Правило: **любая правка формулировок вопросов или порогов = новая версия набора +
повторный замер**. Иначе сравнивать «до/после» бессмысленно: изменилось сразу
несколько переменных.

## 7. Что менять при плохих результатах

| Проблема | Действие |
|---|---|
| Пропуск опасного кейса (FN) | добавить/уточнить детерминированное правило в `src/decision-policy.mjs` + кейс в `tests/fixtures-risk.mjs`; правила держать узкими (FPR) |
| Ложный `ask` (FP) | уточнить регексп правила (якоря `\b`, `$`), либо перевести правило в `medium` (только лог) |
| Laya ошибается на классе задач | упростить критерии, убрать смешение языков в инструкции, проверить `trustworthy`-предупреждения |
| Слишком много токенов на совет роутера | `router log` вместо `advise` |
| Хук заметен по времени | `timeoutMs` вниз + `riskGate.layaPolicy: "smart"`; при p95 Laya > 1 с — `shadow` и проверить `device` |

## 8. Известные ограничения (наблюдения, а не предположения)

- **`risk_class` от Laya на коротких синтетических состояниях слабый.** На
  `git reset --hard HEAD~1` с незакоммиченными изменениями модель отвечает
  `medium`/`low` (p ≈ 0.5–0.7), а не `high`. Именно поэтому правила — основной
  барьер, а Laya — уточняющий слой. Не «улучшайте» это поднятием порога вниз:
  получите ложные `ask`.
- **`task_class` (роутер) шумит — измерено.** На размеченном наборе из 12 промптов
  (`scripts/laya-router-eval.mjs`, набор в `src/router-cases.mjs`):

  | Формулировка | Точность | fast | balanced | deep |
  |---|---|---|---|---|
  | v1: выбор из 3 категорий (было) | 3/12 (25%) | 2/4 | 1/4 | **0/4** |
  | v2/v3: конкретные якоря критериев | 4/12 (33%) | 2/4 | 2–3/4 | **0/4** |
  | v4: те же критерии, обратный порядок | 6/12 (50%) | 3/4 | 3/4 | **0/4** |
  | v5: бинарная пара + пороги 0.7 (стало) | **7/12 (58%)** | 2/4 | 3/4 | **2/4** |

  Два вывода, важных для архитектуры:
  1. **Позиционное смещение**: перестановка вариантов местами дала +25 процентных
     пунктов — модель тяготела к первому варианту, а не оценивала смысл. Любой
     выбор из N вариантов у этой модели обязан проверяться на порядок.
  2. **Три категории не работают, две — работают**: класс deep не распознавался в
     0/4 ни при одной формулировке тройного выбора, но бинарный вопрос «нужно ли
     исследование?» дал 0.89–0.93 на двух deep-кейсах. Поэтому роутер переведён на
     пару `noul`-вопросов с правилом (пороги 0.7 подобраны на замерах:
     `scripts/laya-router-thresholds.mjs`).
  Итог: сигнал остаётся слабым (58%), `router` по умолчанию `log`, автопереключение
  модели запрещено — только рекомендация в режиме `advise`.
- **`collapsed`/`state_dropped` встречаются редко, но не невозможны** на длинных
  состояниях. Плагин их не «исправляет», а помечает ответ `trustworthy: false` —
  решение по такому ответу не принимается.
- **Первый вызов после долгого простоя** может стоить дороже (кэши CUDA).
  `start-laya.cmd` делает прогрев при старте; повторный прогрев после сна машины
  не выполняется — первый вызов просто окажется медленнее (но в fail-open это
  безопасно).
